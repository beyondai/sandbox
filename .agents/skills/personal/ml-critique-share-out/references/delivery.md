# Share-out delivery by context type

Contents: All types | Working-session interview | Team design review |
Launch review

How to deliver a critique share-out well. Select the type that matches the
share-out context. If 2 types fit, use the one with the stricter limit.

## All types

- **Lead with the top 3.** Say them in the first 2 minutes. Reason: if
  time runs out, the most important points are said.
- **Claim, then evidence, then fix.** One sentence for each. Stop and let
  the other side react.
- **Credit before criticism, but only real credit.** Use the strengths
  that are costly to lose. Reason: filler praise reads as politeness and
  weakens the real points.
- **Ask before you assert** when the write-up is vague. "How is P@5
  computed?" is better than "P@5 is wrong". Then give what each answer
  changes.
- **One problem, one fix.** Do not chain 3 problems in one sentence.
- **Keep free time.** About 20% of the limit, for follow-up questions.
- **Track time.** Check the timeline at each block. Move a point to
  Backup instead of rushing it.

## Working-session interview

Example: "review a junior engineer's report, discuss it like a colleague,
be ready to sketch".

- **Tone.** A colleague, not an examiner. Say "I would" and "we could",
  not "you did it wrong". The interviewer plays the author or the lead.
- **Show judgment, not volume.** Say why a point matters more than
  another ("this one first, because it makes all later numbers invalid").
  Reason: the interviewer grades prioritization.
- **Sketch the fix** for each of the top 3 (a split timeline, a pipeline,
  a metric diagram). Keep each sketch to 5-8 lines.
- **Expect follow-ups 2 levels deep.** For each P1, know the next 2
  questions ("how would you build that baseline?", "what if the answer is
  no?").
- **Admit limits.** If you are not sure, say what you would check and how.
- **Keep your questions to the author** for the questions topic, and at
  most 3-5. Pick the ones whose answer changes the plan most.
- **No tools during the session** if the brief says so. The share-out
  file is for preparation only.

## Team design review

Example: "15 minutes in the weekly design review".

- **Start with the verdict** (`ready`, `ready with changes`, `needs
  rework`) and the top 3.
- **Ask for a decision on each P1**: accept, or an owner and a date.
- **Send the full critique** before or after the meeting. The meeting
  covers only the P1 items and the open questions.
- **Name owners.** Each action has one owner.

## Launch review

Example: "go/no-go for the launch on Friday".

- **Lead with the blockers.** A P1 that blocks the launch (safety,
  access control, a wrong metric) comes first, with the condition to
  unblock it.
- **Separate "before launch" from "after launch".** P2 and P3 items go to
  a follow-up list with owners.
- **Give the risk of each open item** in one line: what fails, for whom,
  how often.
