## Change or fix

### P1

**C1. No measurable goal. The metric chain is broken.**
- Evidence: :12-13 ("Engineers say that they cannot find what they
  need"). No number, target, or date.
- Effect: the team cannot decide to launch or to stop. It can optimize
  AUC and not help new hires.
- Alternative: one chain. Goal: find docs faster. Online metric: the
  successful-click rate of the panel (dwell 30 s or more). Offline
  proxy: recall@5. Add a new-hire metric (time-to-find or "where is the
  doc" questions).

**C2. No baseline.**
- Evidence: :71-77 show only the model.
- Effect: nobody can say if the 25.7M-parameter model adds value. The
  P@5 of 0.31 has no floor.
- Alternative: score 4 baselines on the same test set (below). Ship the
  simplest option within the noise of the best (Principle 1).

How to build the baselines. All baselines use the same test set and the
same metric. Only the scoring function changes.

```
 click log --time split--> train months 1-10 | val 11 | test 12
                                 |                        |
            build scorer (no training, or counts only)    queries: each A with a click in month 12
                                 |                        relevant(A): the B's clicked from A (dwell >= 30 s)
                                 v                        |
   for each test A: score all 42K - {A} --> top 5 --> recall@5, nDCG@5, hit@5 --> mean + bootstrap CI
```

- **TF-IDF cosine.** Fit `TfidfVectorizer` (50K vocabulary) on the
  article text at the train cutoff. L2-normalize. Compute
  `scores = X @ X[A].T`. Remove A. Take the top 5. A sparse 42K x 50K
  matrix takes seconds. It tests: does training add value over its own
  input?
- **Co-click.** Count the (A, B) clicks in the train months. Normalize
  so that hub pages do not win: `cooc(A,B) / sqrt(n_A * n_B)`. Take the
  top 5. If A has fewer than 5, fill from TF-IDF. It tests behavior with
  no model. It is usually strong on head articles.
- **Links on page.** Parse the outgoing links of A at the cutoff. Rank
  them by their train click count. Take 5. It tests: does the label only
  learn the link graph? (C4)
- **Popularity.** The 5 most-viewed articles in the train months, the
  same for each A. It is the floor. A model below it is broken.
- **Blend (optional).** `score = cos_tfidf + w * log(1 + cooc)`. Tune
  `w` on the validation month. It is the cheap V0 candidate (C7).

```python
# core of every baseline: score matrix -> top-k -> metric
def evaluate(score_fn, test_queries, relevant, k=5):
    recalls = []
    for a in test_queries:
        s = score_fn(a)            # shape (42K,)
        s[a] = -inf                # remove self
        top = argpartition(-s, k)[:k]
        recalls.append(len(set(top) & relevant[a]) / min(k, len(relevant[a])))
    return mean(recalls)
```

**C3. Wrong primary metric. P@5 is dismissed as "subjective".**
- Evidence: :75-81. "We're happy with the AUC and accuracy numbers.
  Precision@5 is lower, but recommendations are subjective."
- Calculation: with 1 positive to 4 negatives, a constant "no" gets
  4/5 = 0.80 accuracy. The reported 0.85 is only +0.05.
- Effect: neither number tells how good the 5 shown articles are. The
  only product metric is ignored.
- Alternative: recall@5 and nDCG@5 per query, over the full catalog.
  Report the per-query ceiling and catalog coverage. Drop accuracy. Use
  AUC only as a training diagnostic. Interview line: "you already have
  the right metric; make it the primary one."
- Why the AUC is high:
  - ROC-AUC does not change with the class ratio. It is P(score(pos) >
    score(random neg)). The 80% negatives inflate accuracy, not ROC-AUC.
  - PR-AUC does change with the ratio (random = base rate = 0.20). The
    report does not say which AUC (Q2).
  - The real causes: easy random negatives (another topic) and leakage
    from the random split (C5).

```
 test AUC asks:   true B  vs  1 random article  (easy: other topic)
 serving asks:    true B  vs  ALL 41,999        (hard: close neighbors)
```

**C4. The label learns the existing link graph. A click is not
"useful".**
- Evidence: :26-27 ("a user reads article A, then clicks through to
  article B").
- Effect: if most clicks follow a link on A, the model recommends what
  the page already links to. A click with a fast return counts as a
  success.
- Alternative: record the click source. Exclude already-linked articles
  at serving. Add a dwell threshold (30 s or more). Compare with the
  links-on-page baseline. The lenses gave P1 and P2. It stays P1 (a
  wrong label). Q3 confirms it.

**C5. A random event split does not match production.**
- Evidence: :36 ("Split: 80/20 random").
- Calculation: a pair with 2 events that is in test is also in train
  89% of the time (0.32 / 0.36). With 5 events, about 100%. (B, A) also
  leaks into (A, B), because the towers share weights and cosine is
  symmetric.
- Effect: the test score measures memory. The 0.88 is too high.
- Alternative: a time split: train on months 1-10, validate on 11, test
  on 12. Add slices for new pairs and new articles.

**C6. No access-control filter.**
- Evidence: :85-88 return the 5 nearest neighbors with no filter. :9
  lists post-mortems and design specs, which often sit in restricted
  spaces.
- Effect: a recommended title can leak restricted information. Security
  review blocks the launch. A fixed top-5 per article does not work when
  each viewer can see different articles.
- Alternative: precompute the top 50. Filter by the viewer's ACL at
  request time. Keep 5. For v0, index only the articles that all
  employees can see.

### P2

**C7. The complexity fails the gate, and BERT is next.**
- Evidence: :43-48. The first layer has 50K x 512 = 25.6M weights (99.7%
  of the model), about 611 per article. Train AUC 0.97 vs test 0.88.
  :96 ("Explore BERT embeddings").
- Effect: overfitting, a GPU pipeline to maintain, and no proof of value.
  A heavier model on an invalid eval gives numbers that still mean
  nothing.
- Alternative: phase it. Each version keeps the same pipeline. Only the
  scorer changes. Each version must pass a gate before the next.

```
 V0  TF-IDF cosine + co-click blend  ---gate: beats popularity + links-on-page--->
 V1  pretrained text encoder, frozen ---gate: beats V0 by > noise on recall@5---->
 V2  fine-tuned on click pairs       ---gate: beats V1 by > noise, also on slices
     (shared pipeline: batch top-50 table, filters, ACL, logging, rollback)
```

V0: no learned model (days of work).
- Build the baselines from C2. Select the best (often the blend).
- Build the full product pipeline around it: weekly batch, top-50 table,
  filters (C11), ACL (C6), impression logging (M2), dogfood ramp (C18).
- Reason: most of the risk is in the pipeline, not the model. V0 ships
  value and starts the impression log.

V1: frozen pretrained encoder (the cheap form of "explore BERT").
- Use a small sentence-embedding model, for example `all-MiniLM-L6-v2`,
  `bge-small`, or `e5-small`. No training.
- Articles have about 800 words, more than the 256-512 token limit.
  Split each article into chunks of about 256 tokens. Embed each chunk.
  Average the chunk vectors (or embed the title plus the first chunk).
- 42K articles x about 4 chunks = about 170K chunks. That takes minutes
  on 1 GPU.
- Use cosine kNN. Optionally blend with co-click as in V0.
- Gain: semantics (synonyms, paraphrases) that TF-IDF misses, with no
  training pipeline.

V2: fine-tune on clicks (only if V1 leaves a gap).
- Start from the V1 encoder (or TF-IDF + 1 linear layer if V1 failed).
- Train on (A, B) pairs from the train months with in-batch softmax
  (C8b). Take hard negatives from the V1 neighbors.
- Use early stopping on validation recall@5 (C9).
- Gate: recall@5 above V1 by more than the bootstrap CI. Also check the
  new-hire and zero-click slices: fine-tuning on clicks can hurt the
  tail.
- Then compare online with interleaving (M1).

The author's model is a V2-type model with no V0 or V1 to compare with.

**C8a. The cosine score has no temperature.**
- Evidence: :50-53 ("cosine ... binary cross-entropy").
- Calculation: if p = sigmoid(cos), p stays in [0.269, 0.731]. The best
  loss on a positive is 0.313, and dL/ds stays at -0.269 or less. The
  gradient never reaches 0.
- Effect: training keeps pushing all positives to cos = 1 and all
  negatives to -1. In 64 dimensions, not all unrelated pairs can be at
  -1. This wastes capacity and slows convergence. It is P2, not P1: the
  order of the scores still works, and train AUC 0.97 shows that the
  model learned an order.
- Alternative: divide by a temperature, `s / τ` with τ ≈ 0.05. It is 1
  line. Q11 confirms if a scale exists. If it does, the item closes.

**C8b. Pointwise BCE with 4 uniform random negatives.**
- Evidence: :52-53, :60-61.
- Effect: BCE judges each pair alone. Serving asks if B is above all
  other candidates for A. Uniform negatives are too easy, so the model
  learns topic, not order.
- Alternative: in-batch softmax with logQ correction and mixed negative
  sampling.

```
 L(A, B+) = -log  exp(s(A,B+)/τ) / Σ_j exp(s(A,B_j)/τ)

            B_1   B_2  ...  B_1024
   A_1    [ +     -          -   ]
   A_2    [ -     +          -   ]     cross-entropy, target = diagonal
```

```python
eA = F.normalize(tower(xA), dim=-1)          # (1024, 64)
eB = F.normalize(tower(xB), dim=-1)
logits = eA @ eB.T / tau                     # (1024, 1024)
logits = logits - log_q[b_ids][None, :]      # logQ correction
logits = logits.masked_fill(same_item_mask, -1e9)  # mask duplicates and A_i's other positives
loss = F.cross_entropy(logits, torch.arange(len(eA)))
```

- logQ correction: a popular B is a negative in many batches, so the
  loss punishes it too much. Subtract `log(q_B)`, where `q_B` is the
  share of B in the training pairs.
- False negatives: if B_j is also a true positive for A_i, mask it.
- Mixed negatives: add a small shared set of uniform negatives (for
  example 128 per batch). They cover the tail articles that in-batch
  never shows.
- Optional: 1-2 hard negatives per row. Average the A->B and B->A
  losses.

Negative sampling methods compared:

- **Uniform random (current).** Each of the 42K articles has
  probability 1/42K. Mostly tail articles, mostly another topic. Easy.
  Needs extra forward passes. 4 per positive.
- **In-batch.** The B's of the other rows in the batch. Sampled by click
  frequency, so mostly popular, plausible articles. Closer to serving.
  Free. 1023 per positive. Bias: punishes popular items, fixed by logQ.
  Zero-click articles are never in training.
- **Mixed.** In-batch plus a small uniform set. Keeps the hard, popular
  negatives and covers the tail.
- **Hard negatives.** TF-IDF ranks 10-100 for A with no click from A.
  Teaches close order. Risk: no click does not mean not relevant, so
  skip the top ranks and use 1-2 per positive.
- **Impressed, not clicked.** Shown in the panel and not clicked. The
  real negative. Needs the impression log (M2), so only after launch.

If the author keeps BCE, the pos:neg ratio is a hyperparameter (1:4 to
1:20). Tune it on validation recall@5, never on accuracy. Evaluation
never samples: it ranks the full catalog.

**C9. No validation set, and 50 fixed epochs.**
- Evidence: :36 (train and test only), :68 ("Epochs: 50").
- Effect: each choice made on test numbers leaks into test. The
  train-test gap suggests training past the best point.
- Alternative: a validation month. Early stopping on validation
  recall@5 (patience 2-5). Weight decay or dropout on the first layer.

**C10. The vector database is not needed at this scale.**
- Evidence: :86 ("Store them in a vector database").
- Calculation: 42K x 64 x 4 B = about 11 MB. Exact all-pairs kNN is
  about 1.1 x 10^11 multiply-adds: minutes on 1 CPU. Load: 3,400 users x
  about 30 views a day = about 3.5 QPS, about 10 QPS at peak.
- Effect: one more service to run, monitor, and secure, with no gain.
- Alternative: a weekly batch writes `article_id -> top-50 ids` to a
  key-value table. Serve with a lookup and the ACL filter. Use ANN only
  past about 1M articles.

**C11. No ranking stage, re-rank, or filter step.**
- Evidence: :87-88 return the raw 5 nearest neighbors.
- Effect: the top neighbor is the article itself. Template copies fill
  the panel. Deprecated pages and already-linked pages take slots.
- Alternative: the standard 3 stages.

```
 A --> retrieval (embedding kNN, top 50-100)
         --> ranker: score each (A, candidate) with features
               --> rules: remove self, duplicates (cos > 0.95), deprecated, already linked, no ACL
                     --> diversity: at most 2 per space --> top 5
```

- R0, hand-weighted blend (V0 and V1): `w1*cos_text + w2*log(1+cooc) +
  w3*recency + w4*same_space - w5*is_linked`. Tune the weights on the
  validation month. Cheap and explainable.
- R1, learned ranker (later): LightGBM LambdaMART on (A, candidate)
  rows, grouped by A. Same features plus popularity, article type, and
  age. Label: click with dwell. Only after the impression log exists
  (negatives = shown, not clicked), and only if R1 beats R0 by more than
  the noise.
- Reason for the order: with no impression data, a learned ranker trains
  on the same biased click labels. R0 gets most of the gain.

**C12. Feedback loop: weekly retraining learns from the panel's own
clicks.**
- Evidence: :89-90 ("retrain on the latest click data").
- Effect: the articles that the panel shows get more clicks, so they get
  shown more. An article that the panel never shows never gets panel
  clicks. The model learns its own past output, not what users need.

```
 week 1: model shows B for A --> users click B (because it is shown)
              ^                                  |
              |                                  v
 week 2: model learns "A -> B is strong" <-- retrain on clicks incl. panel clicks
```

- Alternative, simplest first:
  1. Log the source of each click (panel, page link, search).
  2. Train only on non-panel clicks.
  3. Later, use panel clicks with inverse-propensity weights.
  4. Exploration: for some views, 1 of the 5 slots shows a candidate
     from ranks 6-50.

**C13. No promotion gate or rollback for the weekly retrain.**
- Evidence: :89-90.
- Effect: a bad week of data or a pipeline bug ships automatically. The
  panels change for no reason each week.
- Alternative: promote only if recall@5 on the latest held-out week is
  at least the current model's minus the noise. Keep the last model and
  table for a one-switch rollback. Log the model version with each
  impression.

**C14. Zero-click articles are only negatives.**
- Evidence: :24 (articles from 3 years), :31 (clicks from 12 months).
- Effect: the catalog and the click window can differ. That is not the
  problem. With uniform negatives, an old article with no clicks in the
  window appears only as a negative. The model learns "old means not
  relevant", even when the content matches.
- Alternative:
  - Keep the 3-year catalog of live, non-deprecated articles.
  - Do not let zero-click articles appear only as negatives. In-batch
    negatives remove them from training. Mixed negatives (C8b) keep the
    tail in view.
  - Report a zero-click slice. The content path (V1) serves them.
  - Ask why the window is 12 months (Q16). The learning curve (M9)
    decides if older logs help.
  - Use the article text as it was at the train cutoff.

## Missing

**M1 (P2). Online evaluation plan.** Offline recall does not prove that
users find docs faster. Run a user-level A/B test (panel vs no panel)
for whole weeks. With 1,700 users per arm and p = 0.3, the MDE is
2.8 x sqrt(2 x 0.21 / 1700) = about 4.4 pp. That is too coarse to
compare 2 models, so compare models with team-draft interleaving.

**M2 (P2). Impression and click-source logging.** Hard negatives, CTR,
bias correction, and the C12 fix all need it. Log the viewer, article,
shown IDs, positions, model version, time, and the click source. Ship it
with V0.

**M3 (P2). New-hire slice.** The stated goal names new hires (:13). With
353 clicks per user per year, heavy users dominate the log. Report by
tenure (90 days or less), new articles, zero-click articles, article
type, and head vs tail.

**M4 (P2). Profile of the click log.** Count the distinct pairs, the
repeat pairs, and the zero-click articles. Report the clicks per user and
per article. Check for bots. These numbers decide C5, C14, and the P@5
ceiling.

**M5 (P3). Monitoring.** Track the empty-panel rate, coverage, exposure
by space, CTR, the share of panel clicks in training, and job health.
Give each an alert threshold and an owner.

**M6 (P3). Privacy of the logs.** The log shows who read which
post-mortem or HR page. Aggregate to pair counts. Drop user IDs after
aggregation. Set a retention period.

**M7 (P3). Scope, stakeholders, and diagrams.** Out of scope:
personalization and search. Stakeholders: the wiki platform team (panel
UI, ACL API), security, and onboarding owners. Add online and offline
diagrams.

**M8 (P3). Reproducibility.** Fixed seeds, a dated data snapshot, a
frozen vocabulary, and a run log.

**M9 (P3). Learning curve.** Train on 3, 6, and 9 months. Plot
validation recall@5. It shows if more click history helps.

## Questions

Each question has the expected answer and what each answer changes.

**Q1. In which sense do engineers "not find what they need" (:12)?**
- Expected: they do not know where to start.
- (a) No start page: a search problem. Improve search first. The panel
  helps only with the next step.
- (b) They land on stale pages: status filters and an owner per article.
- (c) New hires have no reading path: curated onboarding paths.

**Q2. Which AUC (ROC or PR), and how is P@5 computed: which candidates
and which relevant set?**
- Expected: ROC-AUC on the sampled pairs. P@5 is unclear.
- `[user]` addition: ask which AUC. ROC-AUC does not change with the
  class ratio. PR-AUC has a random floor of 0.20 here.
- On a pool of 1 positive and 4 negatives, P@5 is always 0.20.
- If each A has only 1 relevant B, P@5 is at most 0.20. So 0.31 needs
  at least 1.55 relevant items in each top 5 on average.
- AUC 0.88 gives a mean true-B rank of about 5,000. That is a mean. A
  bimodal rank distribution can still give P@5 = 0.31.
- What changes: over the full catalog, report the ceiling and recall@5.
  Over a sampled pool, recompute over all 42K.

**Q3. What share of clicks follow a link that is already on A?**
- Expected: 70% or more.
- High: C4 is confirmed. Exclude existing links.
- Low: the label is closer to "related". Keep it and add dwell.

**Q4. Does the model beat untrained TF-IDF cosine on the same test set?**
- Expected: not measured. The gain is small.
- No gain: ship cosine + co-click. A gain above the noise: keep the
  model and simplify it (C7).

**Q5. How many distinct (A, B) pairs exist, and how many test pairs are
also in train?**
- Expected: most test pairs are also in train.
- High overlap: the test score is memory (C5). Low: still do the time
  split for production fit.

**Q6. "Recommendations are subjective": in which sense?**
- (a) Labels are noisy: add dwell and a graded set of 200-500 queries.
- (b) Many good answers have no click: use recall@k and a graded set.
- (c) Users differ in taste: personalization is later. Slice first.

**Q7. Are there restricted spaces, and does the recommender run as the
viewer?**
- Expected: yes. Then C6 is a launch blocker.

**Q8. How many articles have zero clicks in the 12 months?**
- Expected: 30% or more. Many: the content path carries most panels.
  Few: co-click can be the main signal.

**Q9. Who are the 3,400 users, and how many are new hires?**
- Expected: a few heavy users make most clicks.
- Few new hires: measure them with a cohort before/after comparison and
  a survey, not an A/B test.

**Q10. How are outdated articles marked?**
- Expected: not consistently.
- A status field exists: filter on it. None: down-weight by last-edit
  age and add a report button.

**Q11. How does cosine become a probability? Is there a temperature?**
- Expected: no scale. Then C8a applies. A scale exists: C8a closes.

**Q12. Was any choice (epochs, sizes, lr) made by looking at test?**
- Expected: yes. Then add a validation month and run again (C9).

**Q13. Is there a panel or an impression log today?**
- Expected: no. Then M2 must ship with V0.

**Q14. Why retrain every week?**
- Expected: clicks change slowly, content changes daily. Then use daily
  inference and a monthly retrain behind a gate (C13, C15).

**Q15. How will the "was this helpful?" data be used (:95)?**
- Expected: fewer than 2% respond, with a bias toward strong opinions.
  Use it as a guardrail and to find bad pairs, not as the label.

**Q16. Why is the click window 12 months when articles cover 3 years?**
- Expected: log retention.
- Older logs exist: let the learning curve (M9) decide. They do not:
  keep 12 months and rely on the content path for the tail (C14).

**Q17.** `[user]` **What pos:neg ratio do you use, which sampling
method, and why?**
- Expected: 1:4 uniform, chosen with no comparison.
- What changes: move to in-batch with mixed negatives (C8b). If BCE
  stays, tune the ratio on validation recall@5.

## Decisions and trade-offs

**D1. C1-C6 (all P1): accept.**
- Given up: the current offline numbers. They must be recomputed on a
  new split and metric before anyone can compare.
- Why: each one makes the later results uncertain or invalid.

**D2. C2 and C7: accept. Keep the full baseline guide and the full
V0/V1/V2 guide in this file.**
- Given up: the two-tower model as the starting point.
- Why: the user wants the build steps for the interview discussion.

**D3. C3: accept, with a corrected reason.** An earlier chat claim said
P@5 = 0.31 "does not agree" with AUC 0.88. That was too strong: 5,000 is
a mean rank. The file states the reason as in Q2.

## Conclusion

Verdict: **needs rework.** The serving shape and the hybrid content and
click design are sound. But the label, split, negatives, and metric
make the reported results invalid, and there is no baseline. The model
can be kept only after it beats simple baselines on a correct eval.

Top 3 changes:

1. Set one measurable goal: the successful-click rate of the panel
   (dwell 30 s or more), plus new-hire time-to-find, with a target and a
   date. (C1)
2. Score untrained baselines on the same test set: TF-IDF cosine,
   co-click counts, links already on the page, and popularity. Keep the
   two-tower model only if it beats them by more than the noise. (C2)
3. Replace AUC and accuracy with recall@5 and nDCG@5 over the full
   catalog of 42K articles, computed per query article. (C3)
