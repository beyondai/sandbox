ML System Design Template

The template has 5 sections:

  1 Definition -> 2 High-level -> 3 Deep dive -> 4 Delivery -> 5 Post delivery
  (why, what,     (framing,       (data,         (ship, run,   (learn, grow)
   who)            architecture)   model)         protect)

Contents

  1. Definition ........ Problem, Requirements, Metrics, Team
  2. High-level Design . ML framing, Architecture diagrams, Delivery phases
  3. Design Deep Dive .. Data, Features, Models, Training
  4. Delivery .......... Execution; Deployment, rollout, and testing;
                         Evaluation; Monitoring; Fallback
  5. Post Delivery ..... Analysis, Explainability, Iteration, Democratize


1. Definition: Problem, Requirements, Metrics, Team

This section sets the context. Define the why, what, how, and who of the
project. Do this before the technical design starts.

Problem
  This is the most important section. It gives the business and user
  context.
  - Business, user, and company goals (long term and short term):
    - Define the core problem that the project solves.
    - Say why the project is important now.
    - Name the user pain point that it fixes.
    - Show how it aligns with the company goals for the quarter (short
      term) and the 3-year strategy (long term).

Requirements
  This part defines the scope and the constraints of the system.
  - Features and out-of-scope:
    - List the capabilities that the system must have. Example: "must
      rank a list of items".
    - List what V1 does not include. This controls the scope. Example:
      "no real-time personalization in V1".
  - Scale, latency, and availability:
    - These are the critical non-functional requirements.
    - Scale: the expected load. Example: "10 million requests per
      minute".
    - Latency: the speed. Example: "p99 latency under 100 ms".
    - Availability: the uptime. Example: "99.99% availability".

Metrics
  This part defines how you measure success.
  - Offline and online:
    - Offline metrics measure the model on a static dataset during
      development. Examples: AUC, nDCG, precision, recall.
    - Online metrics measure the real business effect in live A/B tests.
      Examples: CTR, conversion rate, session time.
    - Guardrail metrics make sure that the system does not harm the user
      experience.

Team
  This part maps the people of the project.
  - Stakeholders, collaborators, and dependencies:
    - Stakeholders: the people to keep informed. Example: a Director of
      Product.
    - Collaborators: the teams that you work with each day. Example: the
      Ads team.
    - Dependencies: the work that you need from other teams. Example: "we
      are blocked until the Data Platform team gives access to the new
      user logs".
  - Reuse and cross-functional users:
    - Find existing components or platforms that you can reuse.
    - Name the cross-functional users of the system. Example: "the Data
      Science team uses the model output for its analyses".


2. High-level Design: ML Framing, Architecture, Phasing

This section gives the high-level technical strategy and the roadmap.

ML framing
  Change the business problem into a precise ML problem.
  Example: the business problem "show users better content" becomes a
  learning-to-rank problem. The model predicts the probability of a click
  for each item.

Architecture diagrams
  Make 2 clear diagrams:
  - The online inference pipeline: the real-time request and response
    flow.
  - The offline training pipeline: how the data is processed and how the
    models are trained.

Delivery phases
  Divide the project into phases: crawl, walk, run (V0, V1, V2).
  For each phase, give:
  - the features that the phase delivers;
  - a rough timeline;
  - the number of team members (TMs).
  This shows a practical, iterative plan.


3. Design Deep Dive: Data, Features, Models, Training

This section is the technical core of the design. It gives the details of
the ML system.

Data
  - Online and offline data use, and data engineering:
    - List the data sources.
    - Online: the data that real-time inference needs.
    - Offline: the data that batch training needs.
    - Describe the data engineering work. Example: "build a new ETL
      pipeline that joins the impression logs and the conversion logs".

Features
  - Features and feature engineering:
    - List the features of the model: user features, item features, and
      context features.
    - Describe the difficult feature engineering. Example: embeddings for
      high-cardinality features such as user_id.

Models
  - Candidate models and trade-offs:
    - List the model types that you considered. Examples: logistic
      regression, GBDT, deep neural network.
    - Explain the trade-offs between them: performance, training cost,
      and interpretability.
    - Give the reason for the model that you select for each phase.

Training
  - Loss function, algorithm, labels, and sampling:
    - Loss function: what the training optimizes.
    - Algorithm: the training algorithm.
    - Labels: how you get the ground-truth labels.
    - Sampling: the strategy for problems such as class imbalance, if
      the data needs one.


4. Delivery: Execution, Deployment, Evaluation, Monitoring, Fallback

This section covers how the system goes to production and how it keeps
running.

Execution
  - Roadmap, plans, timelines, and process:
    - This plan has more detail than the high-level phases.
    - Divide the work into epics or milestones, each with a timeline.
    - Describe the team process. Example: "two-week sprints, with a
      stakeholder review each week".

Deployment, rollout, and testing
  Describe how to deploy the new system safely:
  - Rollout plan. Example: "start with 1% of users, and increase over two
    weeks".
  - Testing plan: unit tests, integration tests, load tests.
  - CI/CD strategy.

Evaluation
  - Detailed online and offline evaluation:
    - This part adds detail to the Metrics part of section 1.
    - Online: describe the A/B test design, and how you measure
      statistical significance.
    - Offline: describe the evaluation method. Example: "a held-out test
      set from the last 7 days of data".

Monitoring
  - Online monitoring of system health:
    - List the metrics on the real-time dashboards after launch.
    - System health: latency, error rate.
    - Model health: prediction distribution, feature drift.

Fallback
  - Fallback plans:
    - This is the critical "what if it breaks?" plan.
    - Say what happens when the new model fails in production.
    - Define the fallback mechanism. Examples: "if the new model service
      is down, the system automatically uses the old model", or "use a
      simple ranking by popularity".


5. Post Delivery: Analysis, Explainability, Iteration, Democratize

This section covers the life of the project after a successful launch.

Analysis
  - Result analysis:
    - Say how you analyze the results after the A/B test ends.
    - Describe the deep-dive analysis plan. It must find why a result
      occurred, not only what occurred.

Explainability
  - For other people to understand:
    - Make the model decisions clear to people.
    - Use methods such as SHAP or LIME to explain each prediction.
    - This helps debugging, and it builds trust with stakeholders.

Iteration
  - Future versions:
    - Use the analysis to plan the next versions (V2, V3).
    - Give the future roadmap.

Democratize
  - Benefit to other teams or organizations:
    - This part increases the effect of the work.
    - Find what other teams can share or reuse: the features, the model
      architecture, or the platform components.
    - Name these opportunities to "democratize" the solution.
