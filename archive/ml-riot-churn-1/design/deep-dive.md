# Design Deep Dive: Player Churn and Revival

Practice project (regular design flow, not a timed interview rep or monkey-mode
backfill). Problem statement: "Too many players are drifting away. Figure out
who's at risk and who might come back." Two related, separately-trained models:
a **lapse model** for players currently active, and a **revival model** for
players currently inactive.

Source data: `data/riot-synthetic/synthetic-data/data/lifecycle/` (synthetic,
generated by `riot_practice_data.py`, seed unknown/unrecorded — not re-run for
this project). All numbers below are computed directly from the CSVs, not from
any answer key.

## Data

**Real-time inference sources:** not applicable yet — this is offline batch
scoring, not a live-serving system. Open question for delivery-phase work:
score daily or weekly. Weekly is the reasonable default for a lifecycle model
(engagement patterns don't shift within a day), revisited if the action turns
out to be time-sensitive (e.g. same-day nudges).

**Batch training sources:**
- `players.csv` — 12,000 players. `signup_day`, `region` (EUW/BR/KR/LATAM,
  **29.3% null** — a real data-quality flag, not a synthetic artifact to
  ignore; handled as an explicit "unknown" category rather than imputed),
  `platform` (pc 80.4% / mobile 19.6%, no nulls), `acquisition_source`
  (organic 50.1% / paid_ads 29.7% / friend_referral 20.2%, no nulls).
- `activity.csv` — 748,811 rows, one row per player-day actually played, days
  0-269. 11,771 of the 12,000 players have at least one activity row (229
  players never play at all — they never enter either model's population,
  since neither "active in the last 7 days" nor "signed up and had a chance to
  lapse" applies to a player who never played). Columns: `games`, `wins`,
  `party_games`, `minutes`. No nulls.
- `campaign.csv` — 3,150 players in a randomized comeback-offer campaign sent
  on day 180, half treated. **Not a feature source.** Used only to exclude
  contaminated players from the evaluation population (see Training).
- `content_calendar.csv` — 6 content-event start days (30, 75, 120, 165, 210,
  255), known in advance, legitimate as a feature.
- `purchases.csv` — not used by this project. L1 is an engagement/lifecycle
  problem, not a value problem; spend data belongs to the LTV project.
- `_truth/` — latent traits and true lifecycle state. Not read by this
  project at all (design or modeling) — it's held out as a grading key for a
  version of this exercise where an interviewer would compare it against my
  answer, not an input to my design.

**New data engineering:** `activity.csv` is a sparse player-day log (a player
who plays 60 of 270 days has 60 rows, not 270). Both models need aggregates
over rolling pre-cutoff windows (last 7/28 days) and a "days since last
active" recency feature, none of which exist as columns — they have to be
derived by grouping `activity.csv` by `player_id` and windowing on `day`. The
stretch-goal hazard formulation needs a further transform: one row per
player-active-period instead of one row per player, which is a bigger
reshaping step than the snapshot logistic-regression models need.

## Features

Both models share a **cutoff `c`**: features are built only from
`activity.csv` rows with `day < c` (never from `day >= c`, which is exactly
where the earlier scratch profiling script had a bug — computing "last active
day" over the full 270-day history instead of the pre-cutoff slice, which
silently made every "recently active" player look 100% churned. Caught by the
100% churn rate being obviously degenerate, not by inspection).

**Lapse model** — population: players whose last pre-cutoff active day falls
in `[c-7, c)`. Features, all computed from `activity.csv[day < c]`:
- `active_days_28`, `total_games_28`, `total_minutes_28` — volume over the
  trailing 28 days.
- `win_rate_28` = wins / games over the trailing 28 days.
- `recent_loss_rate_7` = losses / games over the trailing 7 days (the doc's
  "loss streaks predict lapse" probe is about exactly this feature —
  correlation, not something to act on directly).
- `party_share_28` = party_games / games over the trailing 28 days (social
  vs. solo play).
- `avg_minutes_per_active_day_28`.
- `tenure_days` = c - signup_day.
- `days_since_last_active` — doubles as the recency baseline's only input.
- `days_to_nearest_content_event` — signed distance from `c` to the nearest
  `content_calendar` start day, since an event can pull a drifting player back
  before they'd otherwise lapse.
- `region` (with an explicit "unknown" level for the 29.3% null), `platform`,
  `acquisition_source` — one-hot or target-encoded categoricals.

**Revival model** — population: players who signed up before `c-7` and whose
last pre-cutoff active day is more than 7 days before `c` (or who never
played at all pre-cutoff). Features are the same shape but computed over the
player's **entire pre-cutoff history**, not a trailing window, since a lapsed
player's "last 28 days" is mostly empty by construction:
- `days_since_last_active`, `tenure_at_lapse` (signup_day to last active day),
  `lifetime_active_days`, `lifetime_games`, `lifetime_avg_minutes_per_session`,
  `lifetime_party_share`.
- `days_to_nearest_content_event` — the doc flags this explicitly ("try
  including content-event timing"), and it's the one feature that
  differentiates a revival model from a generic recency model.
- `region`, `platform`, `acquisition_source`.

Nontrivial feature engineering: the rolling-window aggregation itself (not a
column that exists anywhere), and the null-region "unknown" category rather
than dropping the ~29% of rows or imputing a guessed region.

## Models

Both models get the same phase structure; they're trained separately because
their populations and feature windows differ.

| Phase | Model | Why |
|---|---|---|
| V0 baseline | `days_since_last_active` alone, thresholded/ranked | No training, cheap to compute, and the number every stakeholder already intuits. Establishes the floor the real model has to beat, and by how much. |
| V1 (primary) | Logistic regression, L2-regularized, trained from scratch (gradient descent) | Interpretable coefficients an offer/retention team can act on directly ("party share matters more than solo minutes"), cheap to serve, and matches the "write the core yourself, use sklearn as a reference" scope for this exercise. |
| V2 (stretch, lapse only) | Discrete-time hazard model: one row per player-active-period, same logistic link, label = "did they stop in this period" | V1 treats "active in the last 7 days" as a fixed snapshot and throws away *when* within that window a player was last seen. A hazard formulation handles that as time-varying risk and handles censoring correctly (a player still active at the end of the observation window isn't a negative example, they're unresolved) instead of quietly mislabeling them. Cost: bigger data reshape (see Data), and the log-likelihood is less immediately readable to a non-technical stakeholder than a single risk score. |
| Reference only | `sklearn.linear_model.LogisticRegression` with matching L2 penalty; optionally `HistGradientBoostingClassifier` as a ceiling check | Not shipped. Used to verify the from-scratch V1 coefficients match a trusted implementation, and to see whether a much more flexible model meaningfully beats V1 (if it doesn't, that's evidence 28-day engagement features are close to sufficient; if it does, that's a feature-engineering gap, not a reason to ship a black box). |

Tradeoff not yet resolved, flagged for the modeling phase rather than decided
here: V1's L2 penalty strength and the choice of one-hot vs. target-encoding
for `acquisition_source`/`region` are both things to cross-validate, not
guess up front.

## Training

**Labels**, both models, at cutoff `c` with horizon H=28 days:
- Lapse: label = 1 ("lapsed") if the player has **zero** `activity.csv` rows
  with `day` in `[c, c+H)`; else 0.
- Revival: label = 1 ("returned") if the player has **any** `activity.csv`
  row with `day` in `[c, c+H)`; else 0.

Both labels are built strictly from `day >= c`, matching the strict
feature/label split above — this is the one invariant worth a unit test
before anything else, given the profiling bug already caught once today.

**Backtesting cutoffs:** train at `c=135` (label window 135-163), evaluate at
`c=180` (label window 180-208). `c_train + H = 163 ≤ c_test = 180`, so no
training label overlaps the test window. Both cutoffs are chosen to align
with a `content_calendar` boundary region rather than mid-event, to avoid one
cutoff falling inside a content spike and the other not.

**Campaign contamination:** the day-180 comeback campaign is sent exactly at
the test cutoff. Per the campaign's own semantics, only the **treated** half
should behave differently from a player who was never in the campaign at all
— control-arm players get no intervention, so they're left in. Computed
class balance:

| Population | n | Positive rate |
|---|---|---|
| Lapse, train cutoff 135 | 4,954 | 8.20% |
| Lapse, test cutoff 180 (treated excluded) | 4,675 | 8.68% |
| Revival, train cutoff 135 | 5,181 | 5.21% |
| Revival, test cutoff 180 (treated excluded) | 5,719 | 4.04% |

**Sampling / class imbalance:** both labels sit at 4-9% positive. Plan is
class-weighted logistic regression (weight inversely proportional to class
frequency) rather than resampling, so the from-scratch gradient descent stays
a straightforward weighted log-loss instead of needing a separate
oversampling step. Revisit if V1's PR-AUC on the weighted model is worse than
an unweighted model evaluated with a shifted decision threshold — that would
suggest resampling is masking rather than fixing the imbalance.

**Loss function:** weighted binary cross-entropy + L2 penalty on the
coefficients (excluding the intercept).

**Training algorithm:** batch gradient descent on the weighted log-loss,
reference-checked against `sklearn.linear_model.LogisticRegression(penalty="l2", class_weight="balanced")`
on the same feature matrix — coefficients should match within numerical
tolerance, which is the correctness check for this project (this data has no
published closed-form answer the way the LTV project's BG/NBD model does).

**Evaluation population, restated:** report metrics only on each model's own
task population (recently-active players for lapse, currently-inactive
players for revival) — never on "all 12,000 players," where the task looks
artificially easy because most players' near-term activity is simply a
continuation of what they were already doing.
